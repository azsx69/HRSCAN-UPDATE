# HRSCAN-UPDATE

ส่งข้อมูลสแกนลายนิ้วมือจากเครื่อง ZKTeco ขึ้น Supabase — ทำงานเป็น Windows service ประจำสาขา ไม่มีหน้าจอ ใช้งานผ่านเมนู CMD

```
เครื่องสแกน ZKTeco ──TCP 4370──▶ HRSCAN-UPDATE ──▶ Supabase ──▶ ระบบ HR
     ที่สาขา                    (service ที่สาขา)              (ดึงไปเองอัตโนมัติ)
```

สาขาที่ลง **ZKBioTime** ไว้ต่อเครื่องสแกนตรง ๆ ไม่ได้ เพราะโปรแกรมนั้นยึดการเชื่อมต่อไว้ตลอด
สาขาแบบนี้ให้ตั้งแหล่งข้อมูลเป็น `biotime` แล้วโปรแกรมจะอ่านจากฐานของ ZKBioTime ในเครื่องแทน

```
เครื่องสแกน ──▶ ZKBioTime (PostgreSQL ในเครื่อง) ──▶ HRSCAN-UPDATE ──▶ Supabase ──▶ ระบบ HR
```

ส่วนที่เหลือทำงานเหมือนกันทุกอย่าง — ตัวจำ (cursor), การกันข้อมูลซ้ำ และการส่งขึ้น Supabase ใช้ชุดเดียวกัน

### การตั้งค่าเฉพาะ Store 2

`Store 2` ใช้เครื่อง **Jaybon02 (MB40-VL) ที่ `192.168.1.69:4370`** และโปรแกรมจะบังคับอ่านจากเครื่องโดยตรง แม้ `config.ini` รุ่นเก่าเคยตั้ง `[source] type = biotime` ไว้ ส่วน Store 1 และสาขาอื่นยังเลือก `device`/`biotime` ตาม config เดิมโดยไม่เปลี่ยนพฤติกรรม

เครื่อง MB40-VL ส่ง attendance packet ขนาด 49 ไบต์ ต่างจากเครื่อง K50/ID ของ Store 1 ที่ใช้ 40 ไบต์ โปรแกรมจึงกำหนด raw parser 49 ไบต์เฉพาะ Store 2 ส่วน Store 1 ยังใช้ตัวอ่านเดิมของ `node-zklib` จากนั้นข้อมูลทั้งสองสาขาจะผ่าน payload, cursor, batch และ Supabase upsert ชุดเดียวกัน

### นำเข้าพนักงานจาก Supabase ไปเครื่องสแกนของสาขา

ระบบรองรับทิศทางกลับสำหรับ **ข้อมูลพนักงาน** โดยใช้ตารางคิว `device_employee_import_queue` — ใช้ได้ทุกสาขา `Store 1` ถึง `Store 5`:

```text
ระบบ HR เพิ่มแถว pending ใน Supabase (ระบุสาขาปลายทาง)
          ↓
HRSCAN-UPDATE ของสาขานั้น claim งานแบบ atomic **ทีละ 1 รายการ** ด้วย lease + claim token
          ↓
เพิ่ม/แก้ไขรหัส ชื่อ และเลขบัตรบนเครื่องสแกนของสาขา โดยชื่อรูปแบบ `ชื่อ .นามสกุล (ชื่อเล่น)` จะส่งเข้าเครื่องเฉพาะส่วน `ชื่อ`
          ↓
อ่านกลับจากเครื่องเพื่อยืนยัน → completed / retry / failed
```

แต่ละสาขาล็อกแยกกัน (advisory lock ต่อสาขา) สาขาที่งานค้างจึงไม่บล็อกสาขาอื่น

1. รัน `supabase/migrations/202608110001_create_device_employee_import_queue.sql` ใน Supabase SQL Editor
2. เพิ่มหมวดนี้ใน `config.ini` ของสาขาที่ต้องการ แล้ว restart service:

```ini
[employee_import]
enabled = true
batch_size = 10
; ไม่ตั้ง worker_id = ใช้ machine_code ของสาขาแทน
```

> เปิดได้เฉพาะสาขาที่ `[source] type = device` เท่านั้น — สาขาที่ใช้ ZKBioTime จะเขียนลงเครื่องไม่ผ่าน เพราะโปรแกรมนั้นยึดการเชื่อมต่อเครื่องไว้ตลอด งานจะ retry จนกลายเป็น `failed`

3. ระบบ HR ฝั่ง backend ที่เก็บ `SUPABASE_SERVICE_KEY` เพิ่มคำขอ (ห้าม insert จาก browser โดยตรง) เช่น:

```sql
insert into public.device_employee_import_queue
  (branch, employee_code, employee_name, request_key)
values
  ('Store 2', '888', 'ทดสอบ 888', 'employee-888-v1');
```

ต้องระบุ `branch` ทุกครั้ง — คอลัมน์นี้ไม่มีค่า default แล้ว เพราะค่า default จะพางานไปลงเครื่องผิดสาขาแบบเงียบ ๆ เมื่อผู้เรียกลืมใส่

`request_key` ต้องไม่ซ้ำและควรมีเลขรุ่นต่อท้าย (`-v1`, `-v2`) — ส่งค่าเดิมซ้ำจะไม่เกิดงานใหม่ ซึ่งเป็นตัวกันสั่งซ้ำ แต่แปลว่าการแก้ชื่อคนเดิมครั้งถัดไปต้องใช้ key ใหม่

`card_number` เป็น optional: ถ้าไม่ส่ง ระบบจะรักษาเลขบัตรเดิมของพนักงานไว้; สำหรับพนักงานใหม่จะใช้ `0` ถ้าต้องการเปลี่ยนบัตรจึงค่อยระบุคอลัมน์นี้

ตรวจผลจาก `status`: `pending` → `processing` → `completed`; ถ้าผิดพลาดจะเป็น `retry` และลองใหม่สูงสุด `max_attempts` ก่อนเป็น `failed` ใช้เมนูข้อ 5 → “นำเข้าพนักงาน” เมื่อต้องการสั่งทันที (เมนูจะหยุด service ชั่วคราวเพื่อไม่ให้แย่งการเชื่อมต่อเครื่อง) โดยปกติ service ตรวจคิวให้อัตโนมัติ

> คิวนี้เพิ่ม/แก้ไขเฉพาะโปรไฟล์พนักงาน ไม่เก็บและไม่ส่งแม่แบบลายนิ้วมือหรือใบหน้า พนักงานใหม่ต้องลงทะเบียนชีวมิติที่หน้าเครื่องภายหลัง และระบบจะไม่ลบผู้ใช้จากคำสั่งในคิวนี้

### ข้อควรรู้ของการเขียนลงเครื่อง

- **เครื่องถูกล็อกชั่วคราวระหว่างเขียน** (`disableDevice` → เขียน → `enableDevice`) กันคำสั่งพลาดเมื่อมีคนแตะนิ้วพอดี ถ้า log ขึ้นว่า "เขียนสำเร็จแต่ปลดล็อกเครื่องไม่ได้" ต้องรีสตาร์ทเครื่องสแกน ไม่งั้นทั้งสาขาสแกนไม่ได้
- **รหัสบนเครื่องกับรหัสในคิวต้องตรงกันหลังเติมศูนย์ 3 หลัก** เครื่องเก็บ `1` แล้วคิวส่ง `001` แก้ได้ตามปกติ แต่เครื่องเก็บ `0888` แล้วคิวส่ง `888` จะถูกปฏิเสธ เพราะการเขียนทับทำให้ประวัติการสแกนของคนนั้นแยกเป็นสองรหัส ให้แก้รหัสในทะเบียน HR ให้ตรงกับเครื่องก่อน
- **พนักงานใหม่ได้ UID ถัดจากตัวสูงสุด** ไม่ใช้ช่องว่างที่คนถูกลบทิ้งไว้ เพราะเครื่องบางรุ่นไม่ลบแม่แบบลายนิ้วมือตามผู้ใช้
- **ล็อกไฟล์ `.sync.lock`** — ทั้ง service และคำสั่ง CLI ที่ต้องคุยกับเครื่องต้องถือล็อกนี้ก่อน สั่ง `node src\cli.mjs` เองตอน service กำลังทำรอบอยู่จะถูกปฏิเสธพร้อมบอกวิธีแก้ (ล็อกนี้คุมเฉพาะโปรเซสที่รันจากโฟลเดอร์ติดตั้งเดียวกัน)

## ติดตั้งที่สาขา

เปิด **CMD** ที่เครื่องของสาขาแล้ววางคำสั่งนี้

```
powershell -c "irm https://raw.githubusercontent.com/azsx69/HRSCAN-UPDATE/main/install/get.ps1 | iex"
```

สคริปต์จะติดตั้ง Git กับ Node.js ให้ถ้ายังไม่มี แล้วดาวน์โหลดโปรแกรมไปที่ `C:\HRSCAN-UPDATE` จากนั้นถามค่าตั้งค่าทีละข้อ

| ถามอะไร | ตัวอย่าง | หมายเหตุ |
|---|---|---|
| Branch code | `Store 1` | ต้องตรงกับที่ระบบ HR ใช้ ไม่งั้นข้อมูลจะไปโผล่ผิดสาขา |
| Machine code | `FP-01` | ไว้ไล่ที่มาของข้อมูลตอนมีปัญหา |
| แหล่งข้อมูล | `1` เครื่องสแกน / `2` ZKBioTime | เลือก `2` เฉพาะสาขาที่ลง ZKBioTime ไว้ในเครื่องนี้ |
| IP เครื่องสแกน | `192.168.88.175` | ถามเมื่อเลือกแหล่งข้อมูลเป็นเครื่องสแกน — ต้องอยู่วง LAN เดียวกับเครื่องที่ติดตั้ง |
| พาธ psql.exe / ชื่อฐาน | `C:\ZKBioTime\pgsql\bin\psql.exe` · `biotime` | ถามเมื่อเลือก ZKBioTime — ปกติกด Enter ใช้ค่าเดิมได้เลย |
| Supabase URL / service key | | ขอจากผู้ดูแลระบบ |
| ความถี่ sync | `5` นาที | |
| เริ่มดึงข้อมูลตั้งแต่ | `2026-01-01` | ข้อมูลที่สแกนก่อนวันนี้จะไม่ถูกส่ง |

ตั้งค่าเสร็จจะทดสอบการเชื่อมต่อให้ทันที แล้วติดตั้ง service ต่อ **ขั้นตอนติดตั้ง service ต้องใช้สิทธิ์ Administrator**

## ใช้งานประจำวัน

เปิด `C:\HRSCAN-UPDATE\install\menu.bat` — ไฟล์เดียวจบ

```
   1. ดูสถานะ + log ล่าสุด            5. สั่ง sync เดี๋ยวนี้ / ดึงย้อนหลัง
   2. ดู log วันนี้ทั้งไฟล์             6. แก้ไขการตั้งค่า
   3. เปิดโฟลเดอร์ log                7. Start / Stop / Restart service
   4. ทดสอบการเชื่อมต่อ                8. อัปเดตเป็นเวอร์ชันล่าสุด
```

ปกติไม่ต้องทำอะไร service ส่งข้อมูลเองทุก 5 นาที เปิดเมนูเมื่ออยากตรวจว่ายังทำงานปกติ หรือเมื่อสงสัยว่าข้อมูลไม่ขึ้น

### ดึงข้อมูลย้อนหลัง

เมนูข้อ 5 แล้วเลือก 2 จะถามช่วงวันที่ แล้วส่งข้อมูลช่วงนั้นขึ้น Supabase (วันสิ้นสุดนับรวมทั้งวัน)

โหมดนี้**ไม่แตะตัวจำของ service** จึงไม่ทำให้ข้อมูลปัจจุบันหยุดส่ง และสั่งซ้ำช่วงเดิมกี่ครั้งก็ได้ ข้อมูลไม่ซ้ำ ส่วนยอด "ส่งสะสม" ในหน้าสถานะจะไม่นับรอบที่ดึงย้อนหลัง

## เวลามีปัญหา

| อาการ | ตรวจอะไร |
|---|---|
| ข้อมูลไม่ขึ้นเลย | เมนูข้อ 4 ทดสอบการเชื่อมต่อ — จะบอกว่าเป็นที่แหล่งข้อมูลหรือ Supabase |
| สาขาที่ใช้ ZKBioTime แล้วต่อไม่ได้ | ตรวจว่าบริการของ ZKBioTime เปิดอยู่ และพาธ `psql.exe` ในการตั้งค่าถูกต้อง |
| ชื่อพนักงานเป็นตัวประหลาด | เมนูข้อ 4 จะแสดงตัวอย่างชื่อ ถ้าอ่านไม่ออกแปลว่า encoding เพี้ยน แจ้งผู้ดูแล |
| เวลาสแกนผิด | ตรวจเวลาที่ตัวเครื่องสแกนก่อน โปรแกรมส่งเวลาตามที่เครื่องบันทึกไว้ |
| service ไม่ขึ้น | ดู `logs\service.err.log` |

log ของโปรแกรมอยู่ที่ `logs\sync-YYYY-MM-DD.log` เก็บย้อนหลัง 30 วัน

## หลักการทำงาน

โปรแกรมจำเวลาสแกนของแถวล่าสุดที่ส่งสำเร็จไว้ใน `state.json` รอบถัดไปจึงส่งเฉพาะแถวที่ใหม่กว่านั้น

**ถ้าส่งไม่สำเร็จจะไม่ขยับตัวจำ** ข้อมูลจึงไม่หาย เพราะ log ยังอยู่ในเครื่องสแกนและรอบหน้าจะส่งซ้ำ ส่วนแถวที่ส่งซ้ำจะไม่กลายเป็นข้อมูลซ้ำ เพราะฝั่ง Supabase กันไว้ด้วย unique constraint ของ `(branch, employee_code, scan_date, scan_time)`

เวลาทั้งหมดเก็บเป็นเวลาไทย ไม่ใช่ UTC

## สำหรับผู้ดูแลระบบ

ออกเวอร์ชันใหม่จากเครื่อง dev

```
install\release.bat v0.2.0 "แก้อะไรไปบ้าง"
```

แล้วให้แต่ละสาขาเปิดเมนูเลือกข้อ 8 เพื่ออัปเดต หากเวอร์ชันใหม่มีปัญหา ข้อ 9 ย้อนกลับได้ และถ้า service ไม่ขึ้นหลังอัปเดต โปรแกรมจะย้อนเวอร์ชันเดิมให้เองอัตโนมัติ

`config.ini`, `.env` และ `state.json` ไม่ได้อยู่ใน git การอัปเดตจึงไม่แตะการตั้งค่าและตัวจำของแต่ละสาขา

### ข้อควรระวังเรื่องความปลอดภัย

repo นี้เป็น **public** — Supabase service key มีสิทธิ์ข้าม RLS ทั้งหมด **ห้ามใส่ลงในไฟล์ใดที่ commit ขึ้น git** ให้อยู่ใน `.env` เท่านั้น ซึ่ง `.gitignore` กันไว้แล้ว หากเผลอ commit key ขึ้นไป ให้ถือว่า key นั้นใช้ไม่ได้แล้วและต้องออกใหม่ทันที การลบ commit ทีหลังไม่ช่วย

### พัฒนาต่อ

```
npm test        # ทดสอบตรรกะแปลงเวลาไทย, cursor, retry, การแบ่ง batch
npm start       # รัน service แบบเห็นหน้าจอ
node src/cli.mjs status | test-source | test-supabase | sync-now
node src/cli.mjs sync-range 2026-07-01 2026-07-31   # ดึงย้อนหลัง ไม่แตะตัวจำ
```
