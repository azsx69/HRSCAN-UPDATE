# ตั้งนาฬิกาเครื่องสแกนอัตโนมัติ (Device Clock Sync) — Design

- วันที่: 2026-09-17
- สถานะ: รอผู้ใช้ทบทวน
- ขอบเขต: HRSCAN-UPDATE เท่านั้น (ไม่แตะ HR.Jaybononline และไม่แก้ schema Supabase)

## ปัญหา

นาฬิกาในเครื่องสแกน ZKTeco เดินคลาดเคลื่อนไปเรื่อย ๆ และรีเซ็ตเมื่อถ่าน RTC ใกล้หมด เวลาที่ผิดจะติดไปกับ log การสแกนทุกแถว แล้วถูกส่งขึ้น Supabase ต่อไปถึงระบบ HR

ตัวอย่างจริง: วันที่ 2026-09-17 เครื่อง MB10-VL ของ Store 4 (192.168.1.201) ช้ากว่า PC 25 วินาที

ตอนนี้ยังไม่มีโค้ดส่วนไหนตั้งเวลาเครื่อง มีเพียง [sync.mjs](../../../src/sync.mjs) ที่ข้าม log ซึ่งเวลาอยู่ในอนาคต

## เป้าหมาย

- service ตั้งนาฬิกาเครื่องสแกนให้ตรงกับเวลาจริงเองทุกรอบ sync
- ไม่ตั้งเวลาเครื่องจากนาฬิกา PC ที่ตัวเองก็ผิดอยู่
- ถ้าการตั้งเวลาล้ม ต้องไม่กระทบการ sync attendance ซึ่งเป็นงานหลัก

## ไม่อยู่ในขอบเขต

- แก้เวลาของ log ที่บันทึกไปแล้ว
- ตั้งเวลาเครื่องของสาขาที่ `[source] type = biotime` (ZKBioTime ยึดการเชื่อมต่อเครื่องไว้)
- ค่าเปิด/ปิดหรือค่า threshold ใน `config.ini`
- แสดงความคลาดเคลื่อนของนาฬิกาในระบบ HR

## การตัดสินใจที่ตกลงแล้ว

| เรื่อง | ตัดสินใจ |
|---|---|
| แหล่งเวลา | ใช้เวลา PC และต้องผ่านการเทียบกับเวลาเซิร์ฟเวอร์ Supabase ก่อน |
| ความถี่ | ตรวจทุกรอบ sync (ตาม `[sync] interval_minutes`) |
| เกณฑ์ตั้งเวลา | ตั้งเมื่อเครื่องสแกนกับ PC ต่างกันตั้งแต่ 10 วินาที |
| สาขาที่ใช้ | ทุกสาขาที่ `source = device` เปิดใช้ทันทีหลังอัปเดต ไม่มีค่าใน config |
| ตำแหน่งในโค้ด | ขั้นใหม่ใน `tick()` ต่อจาก `runSync` และคิวนำเข้าพนักงาน ภายใต้ `.sync.lock` เดียวกัน |

## ลำดับการทำงาน

```
tick() — ถือ .sync.lock
  1. runSync                  (เดิม)
  2. employee import          (เดิม ถ้าเปิดไว้)
  3. syncDeviceClock          (ใหม่ ข้ามเมื่อ source = biotime)
       a. ตรวจ timezone ของ PC ต้องเป็น UTC+07:00 ถ้าไม่ใช่ → ข้าม + warn
       b. HEAD {SUPABASE_URL}/rest/v1/ แล้วอ่าน HTTP Date header
          - ไม่ได้ header หรือ request ล้ม → ข้าม + warn
          - |PC − Supabase| > 60 วินาที  → ข้าม + warn "นาฬิกา PC เพี้ยน"
       c. ต่อเครื่องผ่าน TCP แล้วส่ง CMD_GET_TIME (201)
       d. |เครื่อง − PC| < 10 วินาที → จบ ไม่เขียน log
       e. ≥ 10 วินาที → CMD_SET_TIME (202) ด้วยเวลา PC
       f. ปิด connection → อ่าน CMD_GET_TIME ด้วย connection ใหม่ ต่างจาก PC ไม่เกิน 3 วินาที = สำเร็จ
          ไม่ผ่าน → รอ 1 วินาทีแล้วอ่านใหม่ สูงสุด 3 ครั้ง (VERIFY_ATTEMPTS / VERIFY_RETRY_DELAY_MS)
          (ทดลองกับ MB10-VL ของ Store 4: อ่านใน connection เดิมได้เวลาเก่าเสมอ และเครื่องเปลี่ยนเวลาเสร็จภายในราว 1 วินาที)
```

เหตุผลของลำดับนี้:
- **ทำหลัง `runSync`** เพื่อให้ log ที่อยู่ในเครื่องแล้วถูกอ่านขึ้นไปด้วยเวลาเดิมก่อน การตั้งนาฬิกามีผลกับการสแกนครั้งต่อไปเท่านั้น
- **ใช้ HEAD request** ได้ Date header โดยไม่ต้องดึงข้อมูล จึงไม่เปลือง egress ของ Supabase
- **ไม่เรียก `disableDevice`** เพราะ `CMD_SET_TIME` จบในคำสั่งเดียว คนที่กำลังสแกนอยู่จึงไม่ติดขัด

### เรื่อง timezone

ทั้งระบบถือว่า "เวลาท้องถิ่นของ PC = เวลาไทย" ([thaiTime.mjs](../../../src/thaiTime.mjs) อ่านค่าด้วย `getFullYear`/`getHours`/…) การตั้งนาฬิกาใช้แนวเดียวกัน คือเอาส่วนประกอบวันเวลาท้องถิ่นของ PC ไปเข้ารหัสตั้งลงเครื่อง

ก่อนตั้งจึงต้องตรวจ `new Date().getTimezoneOffset() === -420` ด้วย ถ้า Windows ตั้ง timezone ผิด เวลา UTC ของ PC อาจยังตรงกับ Supabase แต่เวลาท้องถิ่นผิดเป็นชั่วโมง ถ้าไม่มีการตรวจนี้ เครื่องสแกนจะถูกตั้งผิดไปทั้งสาขา

## หน่วยของโค้ด

| หน่วย | ไฟล์ | หน้าที่ |
|---|---|---|
| `encodeDeviceTime(date)` | `src/device.mjs` | แปลง `Date` (อ่านค่าท้องถิ่น) เป็น uint32 แบบ ZKTeco: `((ปี%100)*12*31 + (เดือน−1)*31 + วัน−1) * 86400 + (ชม*60 + นาที)*60 + วินาที` |
| `decodeDeviceTime(value)` | `src/device.mjs` | มีอยู่แล้ว เปลี่ยนเป็น `export` เพื่อใช้ร่วมกับการอ่านนาฬิกา |
| `pcClockDriftSec({ pcNow, serverNow })` | `src/deviceClock.mjs` | ฟังก์ชันบริสุทธิ์ คืนวินาทีที่ PC ต่างจากเซิร์ฟเวอร์ (เรียกก่อนต่อเครื่อง) |
| `decideClockAction({ pcNow, deviceNow })` | `src/deviceClock.mjs` | ฟังก์ชันบริสุทธิ์ คืน `{ action: "ok" \| "set", deviceDriftSec, severe }` — `deviceNow = null` (ถอดรหัสเวลาเครื่องไม่ได้) ถือเป็น `set` + `severe` |
| `describeDrift(sec)` | `src/deviceClock.mjs` | ข้อความ "ช้ากว่า PC X วินาที" / "เร็วกว่า…" / "ตรงกับ PC" ใช้ทั้ง log และ `test-source` |
| `readDeviceTime(zk)` / `writeDeviceTime(zk, date)` | `src/deviceClock.mjs` | ส่ง `CMD_GET_TIME` / `CMD_SET_TIME` บน connection ที่เปิดแล้ว |
| `measureDeviceClockDrift(device, { createZk, now })` | `src/deviceClock.mjs` | อ่านอย่างเดียว สำหรับ `test-source` |
| `fetchServerTime({ url, serviceKey }, { fetch })` | `src/deviceClock.mjs` | HEAD request (แนบ `apikey` header) แล้วคืน `Date` จาก Date header หรือ `null` ถ้าไม่มี header — อ่าน header ได้ไม่ว่า HTTP status จะเป็นอะไร เพราะเราต้องการแค่เวลาเซิร์ฟเวอร์ |
| `createDeviceClockSync({ device, supabase, logger, createZk, fetchTime, now, timezoneOffset })` | `src/deviceClock.mjs` | factory สร้างครั้งเดียวตอน service เริ่ม คืน `syncDeviceClock()` ที่เรียกทุกรอบ — factory ถือตัวจำเวลา warn ล่าสุดไว้ รับ dependency ผ่าน parameter เพื่อทดสอบโดยไม่ต้องต่อเครื่องจริง แบบเดียวกับ `importEmployeeToDevice({ createZk })` |

logger ของโปรเจกต์มีแค่ `info` / `ok` / `err` — คำว่า "warn" ในเอกสารนี้หมายถึง `logger.err` ที่ถูกจำกัดความถี่ ไม่เพิ่ม level ใหม่

ค่าคงที่ใน `deviceClock.mjs`:

| ชื่อ | ค่า | ความหมาย |
|---|---|---|
| `SET_THRESHOLD_SEC` | 10 | เครื่องเพี้ยนตั้งแต่ค่านี้จึงตั้งเวลา |
| `PC_DRIFT_LIMIT_SEC` | 60 | PC ต่างจาก Supabase เกินค่านี้ถือว่า PC ผิด |
| `VERIFY_TOLERANCE_SEC` | 3 | ค่าต่างที่ยอมรับได้ตอนอ่านเวลากลับ |
| `SEVERE_DRIFT_SEC` | 3600 | เพี้ยนเกินค่านี้ให้ log เป็น error (สงสัยถ่านนาฬิกา) |
| `WARN_INTERVAL_MS` | 3,600,000 | warn แบบเดิมซ้ำได้ไม่เกินชั่วโมงละครั้ง |

## การจัดการ error และ log

| สถานการณ์ | การทำงาน | log |
|---|---|---|
| `source = biotime` | ข้าม | ไม่มี |
| timezone ของ PC ไม่ใช่ UTC+07:00 | ข้าม | warn ไม่เกินชั่วโมงละครั้ง |
| ต่อ Supabase ไม่ได้ หรือไม่มี Date header | ข้าม | warn ไม่เกินชั่วโมงละครั้ง |
| PC ต่างจาก Supabase เกิน 60 วินาที | ข้าม | warn "นาฬิกา PC เพี้ยน X วินาที — ตรวจการตั้งเวลาของ Windows" ไม่เกินชั่วโมงละครั้ง |
| ต่อเครื่องสแกนไม่ได้ | ข้าม | ไม่ log ซ้ำ เพราะ `runSync` รายงานไว้แล้ว |
| เพี้ยนน้อยกว่า 10 วินาที | ไม่ทำอะไร | ไม่มี |
| ตั้งเวลาสำเร็จ | — | info "ตั้งเวลาเครื่องสแกน: เดิมช้า/เร็ว X วินาที" |
| เพี้ยนเกิน 1 ชั่วโมง | ตั้งเวลาตามปกติ | error "นาฬิกาเครื่องเพี้ยน X ชั่วโมง — อาจเป็นถ่านนาฬิกา ให้ช่างตรวจ" |
| อ่านกลับแล้วต่างเกิน 3 วินาที | ไม่ throw รอบหน้าลองใหม่ | error |
| error อื่นทุกชนิด | `tick()` ครอบด้วย try/catch แยก ห้ามทำให้ sync หรือ service ล้ม | error |

ตัวจำเวลาของ warn ล่าสุดเก็บใน memory ของ process ไม่เขียนลง `state.json` หลัง restart จึง warn ได้ทันที ซึ่งเป็นพฤติกรรมที่ต้องการ

## เพิ่มใน `test-source`

หลังอ่าน log สำเร็จ ให้แสดงบรรทัด "นาฬิกาเครื่องสแกน: ช้า/เร็วกว่า PC X วินาที" (อ่านอย่างเดียว ไม่ตั้งเวลา) เพื่อให้คนติดตั้งเห็นทันที แสดงเฉพาะเมื่อ `source = device`

## การทดสอบ

**Unit test (`node --test`)**
- `encodeDeviceTime` ↔ `decodeDeviceTime`: แปลงไปกลับแล้วต้องได้ค่าเดิม ครอบคลุมต้นปี/ปลายปี, 31 ธ.ค. 23:59:59, 29 ก.พ. ปีอธิกสุรทิน, ค่าจริงจากเครื่อง .201
- `decideClockAction`: เพี้ยน 9 วิ → `ok`, 10 วิ → `set`, −25 วิ → `set`, 2 ชม. → `set` + `severe`, อ่านเวลาไม่ได้ → `set` + `severe`
- `syncDeviceClock`: PC ต่างจาก Supabase 61 วิ → `skip-pc-drift` โดยไม่ต่อเครื่อง
- `fetchServerTime`: มี header, ไม่มี header, fetch throw
- `syncDeviceClock` ด้วย zk และ fetch ปลอม:
  - ส่ง `CMD_SET_TIME` พร้อม payload ที่ถูกต้อง
  - ไม่ส่งเมื่อ `ok`
  - ไม่ต่อเครื่องเลยเมื่อ PC เพี้ยนหรือ timezone ผิด
  - log error เมื่ออ่านกลับไม่ตรง
  - warn ซ้ำไม่เกินชั่วโมงละครั้ง
- `npm test` เดิมต้องผ่านทั้งหมด

**ทดสอบกับเครื่องจริง Store 4 (.201)**: เป็นการเขียนลงเครื่อง ต้องขออนุมัติผู้ใช้ก่อนทุกครั้ง
1. `test-source` ต้องแสดงความคลาดเคลื่อน (ก่อนทดสอบประมาณ −25 วินาที)
2. เรียก `syncDeviceClock` หนึ่งครั้ง → log "ตั้งเวลาเครื่องสแกน"
3. เรียกซ้ำทันที → ต้องไม่ตั้งซ้ำ
4. ให้คนที่หน้าเครื่องสแกน 1 ครั้ง แล้วเทียบเวลาใน log กับนาฬิกาจริง

## ความเสี่ยง

| ความเสี่ยง | การรับมือ |
|---|---|
| เฟิร์มแวร์บางรุ่นรับ `CMD_SET_TIME` แต่ไม่เปลี่ยนเวลาจริง | อ่านกลับยืนยันทุกครั้ง แล้ว log error |

| ต้องการปิดฟีเจอร์ | ใช้ `install\rollback.bat` ย้อนกลับเวอร์ชัน |
